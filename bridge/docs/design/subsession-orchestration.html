1. 設計の要点

サブセッションは、通常のccpocketセッションを親子関係つきで起動したもの。 Bridgeに複雑なスケジューラーは持たせず、オーケストレーション判断は 親セッションで動くGlobal Skillが担当する。

  • ユーザーが直接対話する中心は親セッション。サブセッションの結果は 親が収集して要約する。
  • サブセッションから別のサブセッションは作れない。階層は常に2段まで。
  • 実行手段はローカルCLI、判断手順はユーザースコープのGlobal Skillに置く。
  • アプリは親子をグルーピングし、サブセッションを折りたたみ・非表示にできる。
  • 親の停止前に、Bridgeがすべてのサブセッションの停止を検証する。
  • ツール承認はサブセッション自身や親エージェントに自動委譲せず、 既存のモバイル承認フローへ戻す。
UIの考え方 Attention Queueを新設しない。親セッションとの会話と、親カードに表示する サブセッション要約が、ユーザーにとってのオーケストレーションUIになる。

2. 目的と非目的

目的

  • 大きなタスクを独立した作業へ安全に委譲する
  • ユーザーが親セッションだけを見ても進行を理解できる
  • worktreeによる書き込み競合の回避を標準化する
  • 失敗・再接続・CLI再試行でも重複起動しにくくする
  • 親停止時に孤立したサブセッションを残さない

非目的

  • Bridge内に自律的なDAGスケジューラーを実装すること
  • サブセッションを無制限に再帰生成すること
  • サブセッション専用の別チャット実装を作ること
  • tmuxのようなraw PTY multiplexerを実装すること
  • 親エージェントが危険操作を自動承認すること

3. 用語

用語 意味 ユーザーとの関係
PRIMARY 親セッション ユーザーが開始した通常のccpocketセッション。 ユーザーが直接対話する。
オーケストレーター Global SkillとCLIを使い、作業分解・サブセッション作成・結果統合を行う 親セッション内のエージェント。 進捗説明と最終報告を担当する。
SUB サブセッション 親セッション内のエージェントがCLI経由で作成した、独立した通常セッション。 原則として親を介して対話する。必要時は直接開ける。
Activity status 現在作業中か、入力待ちか、承認待ちかを表す短期状態。 working、idleなど。
Lifecycle status セッションプロセスが生存しているかを表す状態。 active、stopping、stopped。
ターン ひとつのpromptからresultまでの作業単位。 turnIdで完了待ちと結果取得を対応付ける。
idleは停止ではない エージェントが入力待ちでもプロセスは生きている。 親停止時には、idleなサブセッションも停止対象に含める。

4. Bridgeが守る不変条件

Global Skillの指示だけに依存しない。壊れてはいけないルールはBridgeで検証し、 どのクライアントから呼ばれても同じ結果にする。

親セッション ├── サブセッション ├── サブセッション └── サブセッション サブセッション └── ✕ 子セッション作成不可
  1. primaryはparentSessionIdを持たない。
  2. subsessionは必ず1件のprimaryを親に持つ。
  3. サブセッションからの作成要求は常に拒否する。
  4. 親がstoppingなら、新しいサブセッションを作れない。
  5. 親は自分のサブセッションだけを操作できる。
  6. サブセッションの制御tokenに、作成・兄弟操作・承認権限を与えない。
  7. 生存サブセッションが1件でもあれば、親だけを停止できない。
  8. 親子関係はBridge再起動後も復元できる形で永続化する。

5. アーキテクチャ

Flutter App │ 通常のWebSocketプロトコル ▼ Bridge Server ───────── SessionManager ▲ │ │ local control API ├── 親セッション │ ├── サブセッション ccpocket CLI └── サブセッション ▲ │ 決定論的なJSON入出力 Global Skill ▲ │ タスク分解・委譲・待機・要約 親セッションのエージェント

Bridge

セッションの作成・入力・待機・結果・停止を提供する。 親子制約、権限、停止順序を強制する。

CLI

Bridgeのcontrol APIを呼ぶ薄いクライアント。 stdoutは安定したJSON、診断ログはstderrへ出す。

Global Skill

何を委譲するか、いつ待つか、結果をどう統合するかを判断する。 Bridgeの内部実装は知らない。

Control APIの配置

エージェント向けCLIはBridgeと同じホストで実行されるため、 インターネットへ公開しないローカルtransportを使う。

  • macOS / Linux: user-only権限のUnix domain socket
  • Windows: named pipe
  • アプリ向けWebSocketと同じSessionControlServiceを共有する
  • transportごとにセッション操作ロジックを複製しない

6. データモデル

type SessionKind = "primary" | "subsession";

type ActivityStatus =
  | "starting"
  | "working"
  | "needs_user"
  | "idle"
  | "failed";

type LifecycleStatus =
  | "active"
  | "stopping"
  | "stopped";

interface SessionSummary {
  id: string;
  provider: "claude" | "codex";
  projectPath: string;
  name?: string;

  kind: SessionKind;
  parentSessionId?: string;
  createdByTurnId?: string;

  activityStatus: ActivityStatus;
  lifecycleStatus: LifecycleStatus;

  createdAt: string;
  lastActivityAt: string;
  worktreePath?: string;
  worktreeBranch?: string;
}

互換性のための初期値

古いセッションや古いBridgeが親子情報を持たない場合は、 kind = "primary"として扱う。 parentSessionIdがあるのに親が見つからない場合は、 primaryへ暗黙昇格させず「孤立したサブセッション」として診断可能にする。

永続的な親子参照

runtimeのsessionIdだけに依存すると、Bridge再起動やresumeで関係を失う。 Bridgeのsidecar metadata storeに、provider・project・provider session IDを含む 安定参照を保存する。 

interface PersistedSubsessionRelation {
  child: StableSessionRef;
  parent: StableSessionRef;
  createdByTurnId?: string;
  createdAt: string;
}

interface StableSessionRef {
  provider: "claude" | "codex";
  providerSessionId: string;
  projectPath: string;
}

ターン単位の完了

セッション単位のidle待ちではなく、 promptごとにBridgeがturnIdを発行する。 waitとresultは必ず同じturnIdを指定する。

7. CLI設計

公開概念をsession start --parentにせず、 subsession専用namespaceにする。 親IDは実行コンテキストから決まり、エージェントが任意の親を指定できない。

基本コマンド

# 現在の親セッションとcontrol API接続を確認
ccpocket context --json

# 初期promptと同時にサブセッションを作成
ccpocket subsession start \
  --provider codex \
  --project . \
  --worktree auto \
  --name implementer \
  --prompt-file task.md \
  --idempotency-key issue-123-implementer \
  --json

# 追加の指示
ccpocket subsession prompt <session-id> \
  --prompt-file followup.md \
  --idempotency-key issue-123-followup-1 \
  --json

# 指定ターンの状態変化を待つ
ccpocket subsession wait <session-id> \
  --turn <turn-id> \
  --until completed,needs_user,failed \
  --timeout 60s \
  --json

# 完了結果を取得
ccpocket subsession result <session-id> \
  --turn <turn-id> \
  --json

# 親配下の一覧と停止
ccpocket subsession list --json
ccpocket subsession stop <session-id> --json
ccpocket subsession stop --all --json

出力契約

{
  "schemaVersion": 1,
  "sessionId": "worker-123",
  "turnId": "turn-456",
  "parentSessionId": "orchestrator-789",
  "status": "working",
  "worktree": {
    "path": "/workspace/ccpocket-worktrees/worker-123",
    "branch": "ccpocket/worker-123"
  },
  "appUrl": "ccpocket://session/worker-123"
}
  • 成功時のstdoutは1個のJSON objectだけにする。
  • ログ・警告・進捗はstderrへ出す。
  • エラーも固定schemaのJSONにする。
  • promptは長文やshell quoting事故を避けるため、ファイルまたはstdinで渡す。
  • 名前は表示用途。操作対象の正はsessionIdとする。
  • startとpromptはidempotency keyを受け付ける。
  • waitは有限時間で戻り、Skillが必要に応じて再実行する。
サブセッションから作成を試みた場合 
{
  "schemaVersion": 1,
  "error": {
    "code": "subsession_nesting_forbidden",
    "message": "A subsession cannot create another subsession."
  }
}

8. Global Skill

Skill名はccpocket-orchestrateとし、意図しない並列実行やコスト増加を 防ぐため、原則として明示呼び出しで使う。 

$ccpocket-orchestrate このIssueを実装・テスト・レビューまで進めて

Skillが担当する判断

  • 委譲すべき独立タスクと、親が直接行うべきタスクの判定
  • writerごとのworktree分離
  • 同じworktreeを読むreviewer・testerの順序制御
  • サブセッションIDとturn IDの保持
  • bounded wait、結果取得、追加prompt、最終要約
  • ユーザー情報が必要な質問を親セッションへ戻すこと
  • 結果回収後、再利用しないサブセッションを停止すること

Skillがしてはいけないこと

  • サブセッションへ再委譲を指示する
  • 画面テキストや人間向けCLI出力を解析して状態を推測する
  • 子のツール承認を自動的に許可する
  • 同じworktreeで複数writerを同時実行する
  • 完了結果を取得せず、statusだけで成功と判断する

インストール

ccpocket skill install

CLIと同じ配布物にSkillを含め、Codex・Claudeのユーザースコープへ配置する。 SkillはCLIの最小バージョンを宣言し、互換性がない場合は更新案内を出す。

9. アプリUI

サブセッションは通常セッションとして直接開ける一方、 一覧では親の下へグルーピングし、通常時の情報量を抑える。

デフォルト表示

ccpocket実装 サブセッション 3 · 作業中 2 · 承認待ち 1 Working ▸

展開表示

ccpocket実装 オーケストレーター Working ▾
SUB implementer feature worktree Working
SUB tester 結果確認待ち Ready
SUB reviewer コマンド承認が必要 Needs You

表示ルール

  • サブセッションにはSUBバッジと親に対するインデントをつける。
  • 親カードに子の総数、作業中、承認待ち、失敗数を要約する。
  • 親単位で展開・折りたたみできる。
  • 一覧全体で「サブセッションを表示」を切り替えられる。
  • 非表示中でも、親カードには承認待ち・失敗を表示する。
  • Push通知とディープリンクからサブセッションを直接開ける。
  • 検索結果では、条件に一致したサブセッションを一時的に表示できる。
非表示はアクセス拒否ではない 非表示設定はセッション一覧の認知負荷を下げる表示設定。 履歴、Push、ディープリンク、親からのリンクは引き続き利用できる。

10. 停止設計

InterruptとStopを分ける

操作 親 サブセッション
現在ターンをInterrupt 現在の応答・tool実行を中断 停止しない。作業を継続する。
親セッションをStop 子の停止確認後に停止 すべて停止済みであることが必須。
親をArchive / Delete 関係を保持して履歴操作 生存中ならStopと同じ確認を行う。
サブセッションをすべてStop 生存したまま 親配下だけを一括停止。

親停止のユーザーフロー

1

ユーザーが親セッションの「停止」を選ぶ。

2

Bridgeが生存中のサブセッションを検査する。

3

0件なら親を停止。1件以上なら、名前と状態を含む確認情報をアプリへ返す。

4

アプリは「キャンセル」と「すべて停止」を表示する。 「親だけ停止」は提供しない。

5

すべて停止を選ぶと、Bridgeが子を停止し、process exitを確認してから親を停止する。

確認ダイアログ

このセッションを停止しますか？

3件のサブセッションがまだ生存しています。

  • implementer — Working
  • tester — Ready
  • reviewer — Needs You

［キャンセル］　［全4セッションを停止］

Bridge側の停止アルゴリズム

  1. 親グループのlifecycle lockを取得する。
  2. 親をstoppingへ変更し、新規サブセッション作成を拒否する。
  3. すべてのlifecycleStatus != stoppedな子を再取得する。
  4. 子へ並列に停止要求を送り、process exitを待つ。
  5. 生存中の子をもう一度検索する。
  6. 0件なら、キャンセル要求がないことを確認して親を停止する。
  7. 停止失敗やtimeoutがあれば親を残し、失敗した子を結果に含める。
アプリの事前確認だけでは不十分 確認後、停止実行までの間に子が作成される競合を防ぐため、 最終検証とロックは必ずBridgeで行う。

停止のキャンセル

確認前・確認画面

完全にキャンセルできる。プロセスには何も送らない。 破壊的ボタンよりキャンセルを安全な初期選択にする。

一括停止の実行中

「停止処理を中断」として扱う。まだ停止要求を送っていないセッションと親は残すが、 すでに停止した子は復活させない。

停止後のUndoは提供しない 停止したプロセスは復活できない。履歴から再開する操作は可能だが、 それは「停止の取り消し」ではなく新しいruntimeへの「再開」として扱う。

停止状態

active → stop requested → stopping → exit verified → stopped

stoppingから処理中断した場合、まだ生存しているセッションは activeへ戻す。すでにstoppedになった子は戻さない。

Graceful Degradation

  • 旧Bridgeは新messageにunsupported_messageを返す。
  • 新アプリはサブセッション操作時だけBridge更新案内を表示する。
  • 旧アプリは追加fieldを無視し、すべて通常セッションとして表示できる。
  • 旧アプリのstop_sessionで親停止が来ても、Bridge側の不変条件を優先して拒否する。

12. エラー契約

code 条件 呼び出し側の対応
subsession_nesting_forbidden サブセッションが新しいサブセッションを作ろうとした。 現在のセッション内で作業を続ける。
parent_session_not_found 親が存在しない、または停止済み。 親コンテキストを再取得する。
parent_session_stopping 親の停止処理中に新規作成した。 作成を中止し、停止結果を待つ。
subsession_scope_violation 別の親配下のセッションを操作した。 操作を中止し、ID管理を確認する。
turn_not_found 指定したturn IDが存在しない。 session stateと保持IDを再同期する。
active_subsessions_exist サブセッションを残して親だけ停止しようとした。 確認UIを表示し、キャンセルか一括停止を選ぶ。
stop_group_partial_failure 一部のサブセッションがtimeoutまたは停止失敗。 親を残し、失敗した子の再試行を案内する。
protocol_mismatch CLI、Skill、Bridgeの互換性がない。 具体的な必要バージョンを表示する。

13. 権限と安全性

セッションごとのcontrol context

CCPOCKET_SESSION_ID
CCPOCKET_CONTROL_ENDPOINT
CCPOCKET_CONTROL_TOKEN

Bridgeがセッション開始時にcontrol contextを渡し、CLIは自動検出する。 Global API keyや任意の親IDをpromptへ埋め込まない。

操作 親token サブセッションtoken
自分の状態取得 許可 許可
サブセッション作成 許可 拒否
自分の子をlist / prompt / wait / stop 許可 拒否
別の親配下を操作 拒否 拒否
ツール承認・権限昇格 拒否 拒否

質問と承認の扱い

  • 作業内容に関する質問は、親が既知の情報から答えられる場合に限り転送できる。
  • ユーザーの選好・判断が必要なら、親セッションがユーザーへ質問する。
  • shell、file write、MCPなどのツール承認は既存のアプリUIとPushで人間へ戻す。
  • MVPのCLIにapproveやapprove-allを公開しない。

14. 互換性と永続化

新App + 旧Bridge

サブセッション操作で更新案内を表示する。 通常セッション機能は従来通り利用できる。

旧App + 新Bridge

子は通常の実行中セッションとして表示される。 親停止だけはBridgeが安全側へ拒否する。

CLI + Bridge

schemaVersionとBridgeの最小バージョンを検査する。 不一致はsilent fallbackしない。

Skill + CLI

Skillに必要CLIバージョンを記載し、 ccpocket skill installで同時更新する。

履歴上の見え方

  • 停止済みサブセッションもrecent sessionとして直接再閲覧できる。
  • 親子relationを履歴indexへ反映し、親グループ内に表示できる。
  • 子をresumeして新しいruntimeを作る場合も、同じ親relationを引き継ぐ。
  • 親をarchiveしても、子の履歴を孤立させない。

15. 実装フェーズ

1

SessionControlServiceの抽出

WebSocket handlerからstart・input・list・stopの業務処理を分離し、 AppとCLIが同じサービスを利用できるようにする。

2

Global Skill

明示呼び出しのオーケストレーション手順を配布し、 CLIの正常系・質問・失敗・cleanupを検証する。

group lock、停止進捗、処理中断、partial failure、Bridge再接続を含む E2Eテストを追加する。

16. 受け入れ条件

Bridge / CLI

  • 親セッションから、初期promptつきのサブセッションを作成できる。
  • 同じidempotency keyを再送しても重複作成されない。
  • サブセッションからの作成はBridgeで拒否される。
  • 親は自分のサブセッションだけをlist・prompt・wait・stopできる。
  • turn IDを指定して正しい結果を取得できる。
  • CLI stdoutが成功・失敗ともに安定したJSONになる。
  • Bridge再起動後も親子関係を復元できる。

Flutter App

  • 親とサブセッションを見分けられる。
  • サブセッションが親配下にグルーピングされる。
  • グループを折りたたみ・展開できる。
  • サブセッションを一覧から非表示にできる。
  • 非表示中でも親から承認待ち・失敗を認識できる。
  • Pushまたはディープリンクからサブセッションを直接開ける。

停止

  • 親ターンのinterruptでサブセッションが停止しない。
  • 生存サブセッションがある親を単独停止できない。
  • 確認画面で停止を完全にキャンセルできる。
  • 全サブセッションを停止し、exit確認後に親を停止できる。
  • 一括停止中に新しいサブセッションを作れない。
  • 子の停止に失敗した場合、親が生存したまま結果を表示できる。
  • 親を残したままサブセッションだけを一括停止できる。

Global Skill

  • 明示的な呼び出しから、独立タスクをサブセッションへ委譲できる。
  • 複数writerを同じworktreeで並列実行しない。
  • サブセッションの結果を取得し、親セッションで要約できる。
  • 人間の承認をCLIで迂回しない。
  • 結果回収後、不要なサブセッションを停止できる。
